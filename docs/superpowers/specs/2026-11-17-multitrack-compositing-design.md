# 多轨合成设计稿

- 日期：2026-11-17
- 状态：**已确认并实现**（2026-11-17 用户：「开始推进直到完成」）。执行中的取舍见 `docs/decisions.md` 22–30 和实现计划。
- 前置实验：`spikes/gpu-compositor/README.md`（通过）

## 为什么做

用户要求「先专注于剪辑器的功能」，并选择**先做多轨合成**。台标水印、画中画、片头片尾叠加，以及以后的标题文字、转场、调色，本质上都是「几层画面叠在一起」。MVP 的预览和导出同一时刻只能出一路画面，这些功能一个也做不了。所以多轨合成是后面所有画面功能的地基。

实现路线由用户定：「按性能，拓展性最好的方案」。也就是**在显卡上合成**，预览和导出共用同一个合成器。

## 目标

1. **多条视频轨。** 可以增加、删除；时间轴上越靠上的轨，画面越靠上。音频轨也能增删，顺带做，成本很低。
2. **每个视频片段可调「画面」属性：** 位置、缩放、裁剪（上下左右）、不透明度。用这四项就能做画中画、角落台标、半透明水印。
3. **带透明通道的图片（PNG 等）叠加时保持透明**，边缘不能发黑。
4. **预览上直接拖：** 选中片段后，预览里显示它的边框；拖框内移动，拖角缩放；靠近画面中心线或边缘时吸附。
5. **预览和导出一致：** 两边用同一个合成器，用测试比对像素。
6. **性能不倒退**，指标见下文。

## 不做（这一版）

- 旋转、关键帧动画、混合模式（滤色、正片叠底等）、转场、调色。
- 在合成器里画文字：字幕照旧，预览用 GPUI 文字叠加，导出用 libass 烧录，两边已经对齐过（决策 20）。
- 4K 全屏预览和零拷贝显示。用户 2026-11-17 确认不需要。
- 硬件解码。解码后直接上传 YUV 默认不做，单层性能不达标时才提前做，见「性能指标」一节。
- 隐藏 / 锁定轨道、轨道改名。

## 反目标（技术上能跑也算失败）

- 预览和导出的画面不一致：位置、大小、颜色、透明边缘对不上。
- 单层工程（MVP 现有用法）的播放、拖动、导出比现在变慢或变差。
- 旧的 `.vep` 工程打不开，或打开后画面变了。

## 约束

- 沿用 MVP 的工程要求：模块化；非 UI crate 行覆盖率 ≥ 90%，全工作区 ≥ 80%；最严 lint；`scripts/check.ps1` 是总闸。
- 依赖方向：app → engine / export → render / media → core。新增的 `ve-render` 不依赖 FFmpeg 和 GPUI。
- wgpu 用 **30.0.1**，和 gpui-kit 内部用的同一个版本，Cargo.lock 里只会有一份。
- Windows 10+，后端默认 **DX12**。实测比 Vulkan 略快（190 对 170 帧/秒），而且 Windows 自带。
- 测试机器不保证有独立显卡：测试一律用 **WARP 软件显卡**（`force_fallback_adapter`），只用小尺寸图，已验证可用。

## 技术路线

| | 做法 | 取舍 |
|---|---|---|
| A | 在 CPU 上合成；导出照旧用 ffmpeg 的 `overlay` 滤镜 | 最好测试；但预览和导出是两套实现，以后调色、特效都要写两遍 |
| B | 每层交给 GPUI 当成图片叠 | 最快能做出来；但只支持位置、透明度，扩展不了 |
| **C（用户选定）** | **wgpu 显卡合成器，预览和导出共用；结果回读到内存再显示 / 编码** | 性能和扩展性最好，调色、转场、混合模式以后都只是加着色器；代价是导出流程要重写 |

**实验结论**（游戏占满显卡时测，按最坏情况看）：
- 1080p 四层：合成 + 回读一帧平均 8.7 ms；在 GPUI 窗口里显示 **60.03 帧/秒，掉帧 0 次**。
- 1080p NVENC 导出：118 帧/秒。
- 前提：必须由时钟驱动，即提前排帧、按时钟挑帧。

## 设计

### 1. 模型（ve-core）

**轨道顺序。** `Timeline.tracks` 的顺序就是界面上从上到下的顺序。合成时从最下面一条视频轨开始，往上逐层叠加。现有 `resolve_video` 取第一条有画面的视频轨，也就是最上层，和这个约定一致。

**轨道增删。**
- `add_track(project, kind) -> TrackId`：
  - 新视频轨放在所有视频轨的最上面。
  - 新音频轨放在最后一条音频轨的下面。
  - 不支持新建字幕轨，这一版只有一条。
- `remove_track(project, track)`：轨上的片段一起删除，能撤销；某种类型的最后一条轨不能删。

**片段的画面属性。** 片段新增字段 `transform: Transform`，只对视频轨上的媒体片段（视频和图片）起作用：

```text
Transform {
  x, y: f32       // 画面中心相对画布中心的偏移，单位是画布宽 / 高的比例；0 = 居中
  scale: f32      // 相对「完整放进画布」时的大小；1 = 和 MVP 一样的等比适配
  crop: { left, top, right, bottom: f32 }  // 各边裁掉源画面的比例
  opacity: f32    // 0–1
}
```

- **默认值**：`x = y = 0`、`scale = 1`、`crop` 全 0、`opacity = 1`。这时的画面和 MVP 完全一样：等比放进画布、居中、四周留黑。
- **不变式**（加进 `check_invariants`）：
  - 所有值都是有限数；
  - `scale` 在 0.01–10 之间；
  - `opacity` 在 0–1 之间；
  - 四边裁剪都 ≥ 0，且 `left + right < 1`、`top + bottom < 1`。
- **编辑操作**：`set_transform(project, clip, Transform)`。

**几何是纯函数，放在 ve-core**，预览、导出、界面上的拖拽框三处共用：

```text
layer_rect(canvas: (w, h), source: (w, h), &Transform) -> Rect
```

返回结果是画布像素坐标下的矩形，用 f64 计算，返回 f32。计算步骤：
1. **完整的、未裁剪的**源画面等比放进画布，再乘以 `scale`；
2. 中心放在画布中心加上 `(x·w, y·h)` 的位置，得到「整幅画面框」；
3. 按 `crop` 从整幅画面框的四边往里切，得到实际显示的矩形；纹理坐标同样切掉对应比例。

**裁剪不改变画面的位置和大小（我定的）**：裁掉的边直接消失，剩下的像素原地不动，和 Premiere、DaVinci Resolve 一致。拖裁剪滑块时，画面不会跟着变大或跳位置。预览上的拖拽框框的是实际显示的矩形。

**工程文件升到第 2 版。**
- 读取第 1 版时，缺少的 `transform` 取默认值，画面和以前一样。
- 写出时一律写第 2 版。旧版程序遇到第 2 版文件会按现有逻辑报「版本不支持」，不会把新字段默默丢掉。

### 2. 合成器（新 crate：ve-render）

- **输入**：
  - 输出尺寸；
  - 一组图层，从下往上排：`Layer { pixels: &FramePixels, rect, uv, opacity }`；
  - `FramePixels` 这一版只有一种：`Bgra { width, height, data }`，带预乘透明。以后要加 `Yuv420` 时不用改调用方。
- **输出**，两种：
  - `compose_bgra(...) -> Vec<u8>`：给预览用，紧密排列的 BGRA。
  - `compose_nv12(...) -> (Y 平面, UV 平面)`：给导出用。在显卡上从 RGB 转成 **BT.709 有限范围**的 NV12，读回的数据量只有 BGRA 的 3/8，ffmpeg 也不用再在 CPU 上转颜色。
- **背景**是黑色，空隙就是黑场。
- **混合**用预乘透明：`src + dst × (1 − src.a)`。只有带透明通道的图片要在 CPU 上预乘，一张图只解一次，所以只做一次；不透明的画面不用处理。这样缩放时透明边缘不会发黑。
- **解码尺寸（我定的）**：
  - 预览：仍然缩放到预览上限以内。
  - 导出：按「放进导出画布的大小 × max(scale, 1)」解码，但不超过源画面本身的分辨率。这样放大的画中画不会糊，不放大的层也不会多花解码成本。
- **纹理按「槽位」复用**：尺寸变了才重新分配；每帧只上传像素和每层的参数。
- **显卡选择**：
  - 平常选高性能的硬件显卡；没有就退回 WARP，并记一条日志。
  - 测试时强制用 WARP，构造参数 `RenderConfig { software: bool }`。
- **线程**：一个 `Compositor` 只在一个线程里用。预览和导出各自持有一个实例，各自有自己的 wgpu 设备，互不干扰。

### 3. 颜色

- 解码器（ve-media）在把 YUV 转成 BGRA 时，按素材自身标注的色彩矩阵和范围设置 swscale。素材没有标注时，高度 ≥ 720 按 BT.709，否则按 BT.601。现在的代码没有设置这一项，等于一律按 BT.601。
- 导出时由合成器转成 BT.709 有限范围，输出文件标注 `bt709`（`-colorspace`、`-color_primaries`、`-color_trc`）。

### 4. 预览（ve-engine）

- **解析**：`resolve_layers(project, t) -> Vec<LayerSource>`，从下往上排，每项包含素材、素材内时间、片段、`Transform`。原来的 `resolve_video` 改成取它的最上层，或者直接删掉；具体由实现者决定。
- **视频工作线程的 `render(t)`**：
  1. 解析出所有图层；
  2. **并行解码**：每层一个解码任务，用 `std::thread::scope`；
  3. 交给合成器，得到预览尺寸的 BGRA。

  最后一步的产出和以前一样是 `VideoFrame`，所以帧队列、按时钟挑帧、界面显示这些环节**都不用改**。
- **解码器的键**从按素材改成按「轨道 + 素材」。这样同一素材出现在两条轨上时，各用各的解码器，不会来回跳着定位。帧缓存的键仍是「素材 + 帧号」，可以跨轨复用。
- **解码尺寸**不变：仍然等比缩放到预览上限以内，再由显卡缩放到图层实际大小。这样拖动缩放时不会因为尺寸变化导致缓存失效。
- **画布尺寸**：工程尺寸等比放进预览上限（1920×1080）后的大小。

### 5. 导出（ve-export）

视频改为由我们自己逐帧渲染，再交给 ffmpeg 编码：

```text
解码（每层一个线程，按顺序向前读）→ 合成器出 NV12 → 有界队列 → 写线程 → ffmpeg stdin
ffmpeg -f rawvideo -pix_fmt nv12 -s WxH -r 帧率 -i pipe:0  [音频输入…]
       -filter_complex "[0:v]subtitles=subs.ass[v]; <原有音频链>" …
```

- 第 k 帧对应的时间是 `time_of_frame(k)`，和预览挑帧用的是同一套规则。
- **音频、ASS 字幕烧录、取消、进度、`.ve-part` 临时文件、导出前检查**都沿用现有实现。
- **进度**从「已写入的帧数 / 总帧数」直接算出，不再依赖解析 ffmpeg 的输出。
- **NVENC 失败自动改用 x264** 这条保留。失败在开头几帧就会暴露，这时整段从头重新渲染一次。
- **解码**：每个片段从入点定位一次，之后用 `next_frame` 顺序往前读，直到读到覆盖目标时间的那一帧。素材帧率和工程帧率不同时，规则和预览一致：取时间不晚于目标的最后一帧。

### 6. 界面（ve-app）

- **时间轴**：
  - 左侧加一列轨道头，显示轨道名（V2、V1、A1、S1…）和删除按钮；
  - 上方放「＋ 视频轨」「＋ 音频轨」两个按钮；
  - 片段可以在视频轨之间拖动（`move_clip` 已经支持）。
  - 删除带片段的轨道时先确认；按钮沿用之前定下的「确认 / 取消」样式。
- **属性面板**：选中视频轨上的片段时，多出一个「画面」区：
  - X、Y（%，0 = 居中）；
  - 缩放（%）；
  - 不透明度（滑块，%）；
  - 裁剪：上、下、左、右（%）；
  - 「重置」按钮。

  拖动滑块的整个过程算一步撤销，沿用现有的手势机制。
- **预览直接操作**：选中的片段在当前时间可见时，预览上画出它的边框（用 `layer_rect` 换算到屏幕坐标）。
  - 拖框内：移动；
  - 拖四个角：以中心为基准等比缩放；
  - 移动时，画面中心或边缘离画布中心线或边缘不到 8 个屏幕像素就吸附；
  - 一次拖拽算一步撤销。

### 7. 声音（我定的）

所有轨上片段的原声都照常混音播放，包括画中画和被盖住的层。这和 Premiere、Resolve、剪映的做法一致，也是现有 `resolve_audio` 的行为，所以不用改。不想听某一层的声音，就把它的音量调到最低（-60 dB）。按轨道静音不在这一版的范围内。

### 8. 性能指标

全部用 1080p60 素材、1080p 工程。按用户的要求，**在显卡有负载（如游戏在运行）的情况下也要达标**。

| 场景 | 指标 |
|---|---|
| 单层播放（MVP 的用法） | ≥ 59.5 帧/秒（MVP 是 59.97） |
| 主画面 + 1 个画中画 + 台标 | ≥ 59.5 帧/秒，显示间隔 > 25 ms 的次数 ≤ 0.5% |
| 4 层 1080p 视频 | ≥ 50 帧/秒（记录结果，不作为硬性门槛） |
| 两层时拖动预览 | p99 ≤ 80 ms（MVP 单层是 40 ms） |
| 单层导出 | 不慢于 MVP 的导出速度。动手前先测出 MVP 的基线，写进 plan.md |
| 三层导出 | ≥ 1 倍实时 |

现有的 `--bench-playback` 和 `scrub_latency` 要扩展成能指定多层的版本；导出也加一个测速示例。

**不倒退靠测量来保证，不靠单层快速通道（我定的）。** 预览和导出都只走合成器这一条路，不为单层另开捷径，否则就回到了两套实现。做法：
1. 第一步先量出 MVP 的基线：单层导出速度、单层拖动延迟。
2. 合成器接进去以后用同样的方法再量。
3. 如果单层没有达标，就把「解码后直接上传 YUV、在显卡上转颜色」提前到这一版来做。它能省掉 CPU 上的 swscale 颜色转换，上传量降到 3/8，接口已经为它留好了。
4. 实验里 118 帧/秒的导出速度用的是合成出来的测试画面，不含解码，所以不能当作证明，以实测为准。

### 9. 测试

- **ve-core**：
  - `layer_rect` 和裁剪纹理坐标：表驱动用例，加属性测试，验证未裁剪时结果矩形和源画面等比、`scale = 1` 时恰好放进画布，以及裁剪只会缩小矩形、不会移动没被裁的边；
  - `Transform` 的不变式；
  - 轨道增删和撤销；
  - 第 1 版工程文件能读进来，取默认值。
- **ve-render**（WARP，64×36 这类小画布）：
  - 不透明图层的位置精确到像素；
  - 不透明度混合的数值误差在 ±1 以内；
  - 裁剪；
  - 半透明 PNG 缩放后边缘不发黑；
  - NV12 转换结果和 BT.709 公式算出的值相差在 ±1 以内；
  - 槽位尺寸变化后重新分配。
- **一致性**（ve-export 集成测试）：同一个三层工程、同一个时间点，比对预览合成出的 BGRA 和导出文件里那一帧（导出用 x264 `-qp 0`）。PSNR ≥ 35 dB，并且画中画边界的位置误差 ≤ 1 像素。
- **界面**：
  - 加轨、删轨（含确认框）；
  - 在属性面板改画面属性；
  - 在预览上拖动移动和缩放，并验证这些操作各算一步撤销。
- **覆盖率**：ve-render 也要 ≥ 90%。

## 留给实现者

- `resolve_video` 是删掉还是改成取最上层。
- 合成器内部怎么组织：一个渲染管线还是几个、uniform 怎么布局、NV12 用两个渲染目标还是计算着色器。
- 导出的队列深度和线程划分，只要达到性能指标即可。
- 轨道头的视觉样式。要用定制过的主题，不用默认样式，沿用 `theme.rs`。
- 吸附的具体实现，阈值 8 像素是定的。

## 决策记录（实现时追加到 docs/decisions.md）

- 显卡合成，预览和导出共用一个合成器（用户选）。
- 显示走回读，不做零拷贝；不需要 4K 全屏预览（用户 2026-11-17 确认）。
- wgpu 30.0.1，和 gpui-kit 同一版本；后端默认 DX12；测试用 WARP。
- 视频在合成器里转 NV12 后交给 ffmpeg 编码；字幕仍然由 libass 烧录。
- 颜色：解码按素材标注的矩阵，输出用 BT.709 有限范围。
