# gpu-compositor 实验

一次性实验，不进正式代码。验证「wgpu 在显卡上合成多层画面 → 读回内存 → GPUI 显示 / ffmpeg 编码」能不能撑住 60 帧。

场景：4 层。渐变背景铺满；两个画中画，源画面和输出同尺寸，在显卡上缩小，其中一个不透明度 85%；一个 256×256 的半透明圆形台标。每帧重新上传全部层。

```sh
cargo run --release -- bench  --out 1920x1080 --frames 300     # 不开窗口：上传 + 合成 + 读回
cargo run --release -- window --out 1920x1080 --seconds 20     # GPUI 窗口实际显示帧率
cargo run --release -- export --out 1920x1080 --frames 600     # 合成 → 管道 → ffmpeg h264_nvenc
```

## 结果（2026-11-17，RTX 5090，wgpu 30 / Vulkan）

测试时《战神：诸神黄昏》同时在运行，显卡占用 77–98%。用户的判断是：重负载下表现好，空闲时只会更好。所以下表按**最坏情况**理解。

| 项目 | 1080p 输出 | 4K 输出 |
|---|---|---|
| 每帧：上传 + 合成 + 读回 | 平均 8.7 ms，p99 14.5 ms | 平均 14.1 ms，p99 21.5 ms |
| 不开窗口时的吞吐 | 115 帧/秒 | 71 帧/秒 |
| GPUI 窗口显示 | **60.03 帧/秒，掉帧 0 次，显示间隔最长 19.6 ms** | 30.9 帧/秒 |
| NVENC 导出 | 118 帧/秒，约 2 倍实时 | 52 帧/秒，0.86 倍实时 |

## 结论

1. **方案可行。** 1080p 预览在显卡被游戏占满时仍然稳定 60 帧，合成一帧只用掉帧预算的一半左右。
2. **必须由时钟驱动。** 合成线程提前排帧、每帧带帧号，界面按时钟挑当前该显示的那一帧，这和现有引擎的做法一致。第一版让合成线程用 `sleep` 卡节拍，只有 36.6 帧/秒：Windows 上 `sleep` 的精度约 15.6 ms，醒晚了就会连着补帧，多出来的帧被丢掉。
3. **4K 输出慢在搬运，不在合成。**
   - 预览：每帧要把 33 MB 的图交给 GPUI 再上传一次，界面每秒只能重绘 44 次。但预览区的尺寸不会超过窗口，用不到 4K 输出。
   - 导出：慢在每帧上传 3 张 4K BGRA 图（约 100 MB），以及 ffmpeg 在 CPU 上把 BGRA 转成 YUV。
   - 正式版的解法：解码后的 YUV 直接上传（数据量只有 BGRA 的 3/8），颜色转换放在显卡上，读回用双缓冲。如果以后真要 4K 预览，再把显示换成零拷贝。
